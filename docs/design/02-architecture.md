# 02 · 系统架构：六层怎么串成一套贾维斯

下面是一套**可落地、可演进**的参考架构。特点是：
- **本地优先（隐私）**：核心推理和记忆跑在你自己机器上。
- **MCP 工具总线**：所有"手脚"通过统一协议接入，加功能不重构。
- **分层解耦**：某一层换技术（比如把 Ollama 换成云端 API），不影响其他层。

---

## 整体结构（自上而下）

```
┌──────────────────────────────────────────────────────────┐
│                     交互层 Interface                       │
│   语音输出(TTS)   可视界面(Web/桌面/全屋屏)   移动端/穿戴    │
└───────────────────────────┬──────────────────────────────┘
                            │ 你说的话(文本) ↑ 它的回答(文本/语音) ↓
┌───────────────────────────▼──────────────────────────────┐
│                   感知层 Perception                        │
│   唤醒词(openWakeWord) → ASR(FunASR/Whisper) → 文本        │
│   视觉(摄像头+VLM)   传感器(温度/心率/位置)                │
└───────────────────────────┬──────────────────────────────┘
                            │ 用户意图(文本/图像)
┌───────────────────────────▼──────────────────────────────┐
│             认知 / 编排层 Cognition & Orchestration        │
│   LLM 大脑(Ollama: Qwen/DeepSeek)                         │
│   编排器(LangGraph / n8n)：规划 → 调工具 → 反思 → 回答     │
│   人格系统(Persona prompt + 主动规则引擎)                  │
└──────┬───────────────────────────────┬───────────────────┘
       │ 存/取                        │ 调工具
┌──────▼──────────┐          ┌─────────▼──────────────────┐
│  记忆层 Memory   │          │       行动层 Action          │
│ 向量库(Chroma)   │          │  MCP 工具总线               │
│ 结构化(SQLite)   │          │  ├ 设备(Home Assistant)     │
│ 用户画像(JSON)   │          │  ├ 自动化(n8n)              │
│ 对话历史         │          │  ├ 外部API(天气/日历/搜索)   │
└─────────────────┘          │  └ 健康数据(穿戴/健康APP)    │
                             └─────────────────────────────┘
```

## 数据流转（一次完整交互）

1. **静默监听**：感知层用 openWakeWord 只在检测到"贾维斯"时才唤醒，省算力。
2. **语音→文本**：唤醒后录音，FunASR 转文字。
3. **入脑**：文本 + 短期上下文 + 检索到的长期记忆 → 送给 LLM。
4. **规划**：编排器让 LLM 判断——是直接回答，还是调工具（如"查今天日程"）。
5. **行动**：若需工具，通过 MCP 调用对应服务，拿回结果。
6. **生成**：LLM 综合结果生成回答。
7. **输出**：TTS 念出来 + 界面上显示；重要事项写入长期记忆。
8. **主动巡检**（异步）：人格/规则引擎定时检查（"该喝水了？血压异常？"），主动触发交互。

## 关键设计决策

### 1. 本地 vs 云端 大模型
| | 本地(Ollama) | 云端 API |
|---|---|---|
| 隐私 | ✅ 数据不出机 | ⚠️ 需信任厂商 |
| 成本 | 一次性硬件 | 按量付费 |
| 效果 | 中(看模型大小) | 高(大模型) |
| 延迟 | 看机器 | 网络依赖 |

**建议**：本地为主（Qwen3-8B/14B 级别够用），复杂任务 fallback 到云端。健康数据**强制本地**。

### 2. 为什么用 MCP
MCP（Model Context Protocol，Anthropic 提出的开放标准）相当于"AI 的 USB-C"。
好处：工具即插即用、模型无关、社区已有海量现成 MCP Server。你将来接健康 APP、接智能家居，都走这一根线。

### 3. 编排器选 LangGraph 还是 n8n
- **LangGraph**：代码式、适合复杂状态机、多步推理，开发者友好。
- **n8n**：拖拽式、非程序员也能搭流程、自动化强。
- **建议**：MVP 用 LangGraph（灵活）；纯自动化流程可用 n8n 补充。

### 4. 记忆的双库设计
- **向量库（Chroma/Qdrant）**：存"语义记忆"——你说过的话、知识，按意思检索。
- **结构化库（SQLite + JSON 画像）**：存"事实记忆"——姓名、用药、偏好，精确查询。
两者配合，既"懂你意思"又"记准事实"。

## 与你的"健康中枢 APP"如何融合

你本来就规划了一个健康中枢 APP。贾维斯可以是它的**语音入口 + 主动智能层**：

```
健康穿戴数据 → MCP → 贾维斯(感知异常)
                      ↓
              主动提醒("心率偏高，要不要测血压？")
                      ↓
              调用健康APP功能 / 记录 / 建议
```

这样贾维斯不是孤立项目，而是你健康产品的"智能副驾"——和你之前定的"阿枢"定位完全一致。
