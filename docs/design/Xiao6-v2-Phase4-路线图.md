# 小6 v2 — Phase 4 总体路线图（四个方向并行）

> 状态：草稿 · 待批准
> 背景：Phase 1（Context Engine）、Phase 2（EventBus / 世界模型 / 人格引擎）、Phase 3（Goal System）已全部落地入库。
> 范围：用户批准 Phase 4 一次性推进四个方向 —— A 前端 Premium 重构、B 持久知识库 RAG、C 主动智能深化、D 多端同步。
> 纪律：每阶段先有设计、批准后实现；每轮小步（≤3 改文件 / ≤5 新文件 / ≤500 行）；不推翻现有架构，统一用 FEATURE flag 门控；旧行为可回退。

---

## 1. 总目标

小6现在「脑子厚、壳子薄」：55+ 工具、目标系统、主动提醒都到位了，但 UI 还是朴素原生 JS，记忆非语义，主动性被动，且只能在单一 Electron 端点用。

Phase 4 要把它从「能力驱动的工具有机器」升级成「有质感、有记忆、会主动、能多端」的个人副驾。四个方向分工明确：

| 代号 | 方向 | 定位 | 类比 |
|---|---|---|---|
| **P4-A** | 前端 Premium 重构 | 壳 | 把毛坯房精装 |
| **P4-B** | 持久知识库 RAG | 脑 | 长期记忆 + 语义检索 |
| **P4-C** | 主动智能深化 | 魂 | 从被动应答到主动建议 |
| **P4-D** | 多端同步 | 通道 | 手机/网页也能用 |

---

## 2. 依赖关系与推进顺序

```
        P4-A 前端重构（壳，无依赖，立刻可见收益）
              │  提供高级展示层（卡片/面板/动效）
              ▼
        P4-B 持久知识库 RAG（脑，后端独立，可与 A 并行启动）
              │  提供跨会话语义记忆
              ▼
        P4-C 主动智能深化（魂，依赖 A 的展示 + B 的数据）
              │
              ▼
        P4-D 多端同步（通道，架构层，可独立于前三者，最后做）
```

**建议顺序：A → B → C → D。** 理由：
- A 无依赖、纯视觉、风险最低、立刻提升体验，且后续功能都需要好壳子承载，先做。
- B 是纯后端能力，不依赖前端，可在 A 进行到中段时并行启动。
- C 必须站在 A（展示主动建议的 UI）和 B（语义记忆素材）之上，放第三。
- D 涉及部署/鉴权/安全边界，且用户当前主要桌面使用，放最后，不影响前三项价值兑现。

## 3. 各方向关键决策点（待批准）

### P4-A 前端 Premium 重构
- **D1 技术栈**：继续原生 ES Module（Electron 零侵入壳已验证），还是引入 Vite 等构建工具？
  → 倾向：**继续原生 ESM + 建立设计系统**（CSS 变量 + Flux 风格组件层 + 独立 Three.js 背景模块）。不引入构建链，保持 Electron 壳零侵入、可热改。
- **D2 视觉语言**：沿用现有 token（青 `#22D3EE` / 青绿 `#2DD4BF` / 琥珀 `#F5B544`，Orbitron+Rajdhani+Share Tech Mono，玻璃拟态 + 网格扫描线），还是另起一套？
  → 倾向：**沿用并深化现有 token**，做成更精致的高级版（更克制的光效、更稳的层级）。
- **D3 动效预算**：打字机、卡片入场、面板过渡、背景粒子。统一要求 60fps、尊重 `prefers-reduced-motion`、主题切换瞬时无闪烁。
- **D4 回退**：旧 UI 样式保留为 `legacy` 分支，FEATURE flag 可一键回退，避免精装翻车。

### P4-B 持久知识库 RAG
- **D5 向量方案**：本地重依赖（sentence-transformers 体积/CPU 吃紧）vs 轻量方案（调用 Agnes embedding API + 本地 NumPy/FAISS 存储）？
  → 倾向：**Agnes embedding API 生成向量 + 本地轻量索引**（NumPy 内存索引或 SQLite 存向量），零重依赖、跨平台稳。
- **D6 数据来源**：聊天历史归档、文档上传（txt/md/pdf）、网页剪藏。首轮先做聊天历史 + 文档上传。
- **D7 检索注入**：在 Context Engine 新增 `KNOWLEDGE` Source（参照现有 `GOAL`/`PERSONALITY` Source 范式），按相关性/新近度打分注入。
- **D8 隐私**：向量与原文均存本地库，绝不外传；embedding 调用走既有 Agnes 通道（已合规）。

### P4-C 主动智能深化
- **D9 主动建议触发**：基于「Goal 进度 + 时间节律 + 知识库命中」何时主动推「下一步建议」？
  → 倾向：目标有停滞（N 天无进展）时推一步可行动作；每日简报增加「今日建议」段。
- **D10 复盘粒度**：目标完成时复盘（已有）、每日简报复盘、可选的每周小结。
- **D11 展示**：主动建议复用现有 proactive 推送 + 场景卡（scene）能力，不新建通道。

### P4-D 多端同步
- **D12 方式**：同源后端 + 受控 Web 客户端（本地端口 + token 鉴权，默认关闭）vs P2P？
  → 倾向：**同源后端 + 受控 Web 客户端**，复用现有 `/api/*`，加一层 token 鉴权。
- **D13 安全**：继承 Phase C 远程会话安全基线——远程默认禁止 `run_shell`/`file_write`/委托/工厂等高危工具；敏感操作仍需本机确认。
- **D14 默认**：多端通道默认关闭，仅本机 + 显式配置开启，不引入远程控机风险（与既有安全原则一致）。

## 4. 第一轮落地建议（批准后先动这个）

**P4-A 的 MVP（纯视觉升级，零功能改动）：**
1. 建立设计系统：`styles.css` 抽成 CSS 变量 + 组件类（玻璃卡、霓虹描边、网格背景）。
2. 聊天区 / 面板 / 模态升级为玻璃拟态 + 入场动效。
3. 引入轻量 Three.js 背景模块（粒子/网格，性能预算内）。
4. 主题切换瞬时无闪烁、尊重 reduced-motion。

低风险、立刻可见，且为 B/C 的展示层打底。功能逻辑一行不动，靠 FEATURE flag 可回退。

## 5. 风险与纪律
- 四个方向各自用独立 FEATURE flag（如 `FEATURE_PREMIUM_UI` / `FEATURE_KNOWLEDGE_RAG` / `FEATURE_PROACTIVE_V2` / `FEATURE_MULTI_DEVICE`），互不影响、可独立开关。
- 每轮小步提交，不梭哈；旧行为保留回退路径。
- 不推翻 Phase 1-3 架构；新 Source/工具按既有范式（ContextSource / TOOLS / detect_intents）接入。
- 真机验证：每项完成后重启 Electron 走查，而非仅单元烟测。
