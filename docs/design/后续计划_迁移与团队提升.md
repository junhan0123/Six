## 二、战略判断（资深视角，请先读这段）

**白龙马 ≠ 可复制的代码，而是一套理念 + 一堆能力。** 它本质是 Node/Electron/Remix 大型桌面 Agent（Electron 壳、Remix 前端、本地 Agent 委托、媒体生成、社交连接器等），技术栈与小6（Python 标准库单文件后端 + 原生 JS HUD）完全不同。

因此"全部搬过来"的正确解读是：**搬高价值的能力与理念，不是搬代码、更不是把小6也改成 Electron**。盲搬会带来两个灾难：
1. 小6本就是 2000 行 god-file，再塞进白龙马的几十个工具/面板，会变成无法维护的怪物；
2. 白龙马的很多能力依赖外部密钥（MiniMax 媒体、微信 ClawBot、阿里/讯飞 ASR 等），没有密钥就是空架子。

**三条迁移原则：**
- **架构先行**：先拆 god-file，再吸收新能力（否则无从下手）。
- **价值优先 / 本地优先 / 零密钥优先**：先搬不需要外部账号就能跑、且直接提升核心体验的能力。
- **安全闸门不松**：新增文件/Shell/Web 工具必须有沙箱与密钥治理，这是团队从"原型"到"产品"的生死线。

## 三、分阶段计划

### Phase 1 — 工程地基（前置，约 1–2 周）
**目标：让小6能安全、并行地吸收新代码。这是后续一切的前提。**

- **1.1 拆分 god-file `server.py`（最优先）**
  按职责拆为模块：`core/http_routes.py`、`core/db.py`、`core/llm_client.py`、`tools/`（weather、hotspots、notes、calculator…）、`core/memory.py`、`core/proactive.py`（心跳/SSE）。目标：单文件 < 400 行，可独立单测。
- **1.2 质量门禁落地（PR-1.5）**
  装 dev 工具跑一遍 `ruff`/`black`/`mypy` 并修告警；加 `pre-commit` 钩子 + 一个最简 CI（GitHub Actions / 本地脚本二选一）；写 `CONTRIBUTING.md` 与 `CODE_REVIEW_CHECKLIST.md`。
- **1.3 测试基建**
  为纯函数补 `pytest`：计算器 `ast` 沙箱、天气/热点解析、记忆压缩逻辑（这些现在只有 `e2e_*.py` 粗测）。
- **1.4 小修**
  装 `psutil` 恢复 `sysmon`；把 `tool_calculator` 里的 `eval` 换成更明确的安全解释器（评审 P1-3，单独 PR）。

**完成门禁**：`ruff`/`black`/`mypy` 零告警；核心纯函数有单测；新 PR 必须过 pre-commit。

### Phase 2 — 记忆与上下文升级（本地优先、零密钥）
**目标：直接强化小6"会记住、会准备"的核心，全部用本地 SQLite，无需任何外部密钥。**

- **2.1 中文全文检索**：SQLite FTS5 + `trigram` tokenizer，替换现有 LIKE 检索（白龙马已验证中文子串搜索有效）。
- **2.2 用户画像注入**：从对话中抽取角色/领域/偏好，注入 ACI 上下文（白龙马 §8.5）。
- **2.3 线索/焦点栈**：支持多开放话题 + 指代消解（"那个网页""进度怎样"），解决话题漂移（白龙马 §8.6–8.7）。
- **2.4 意图驱动工具选择**：按消息意图/是否有任务/Tick 与否动态裁剪工具 schema，省 token、降误调用（白龙马 §9.2，`find_tool` 自发现）。

**完成门禁**：召回质量有量化指标（命中率/注入量/耗时）；单测覆盖检索与画像抽取。

### Phase 3 — 能力迁移（价值优先）
**目标：把白龙马里"本地能跑、体验增益大"的能力搬进小6。**

- **3.1 多步任务续跑**：`set_task` / `update_task_step` / `complete_task`，重启可恢复（白龙马 §7.5）。小6现有 `reminder` 基础可复用。
- **3.2 工具系统 + 沙箱**：文件读写、Shell 执行、网页抓取（`web_search`/`fetch_url`）。**必须配套**沙箱路径检查、危险操作确认、行动日志（白龙马 §10.2–10.4、§20.5）——这是安全评审重点。
- **3.3 面板扩充**：人物卡片（§15.4）、世界杯面板（§15.3）等"信息看板"类，纯前端+公开 API，零密钥，体验增益明显。
- **3.4 Scene Protocol（可选、高价值）**：把小6 HUD 从手写 JS 改为"声明式 scene"（`UI = f(scene)`，§17）。这是白龙马最创新的点，但前端改造量大，建议作为 Phase 3 的延伸探索，而非必交付。

**完成门禁**：新增工具通过安全评审；面板有单测/快照。

### Phase 4 — 外部/密钥依赖（按需、可选）
**目标：在密钥齐备且老板确认后再做，全部走环境变量、失败优雅降级。**

- 媒体生成（图片/音乐/视频，MiniMax 等）
- 社交扩展（Discord / 飞书；微信已有 `_wx_server` 桥接，可加固）
- 语音 ASR（阿里/讯飞/Volcengine）
- Electron 桌面壳 + 自动更新（仅在决定做桌面端时）

**完成门禁**：所有外部密钥仅存 `.env`；任一 provider 失败不影响主链路。

## 四、团队技术提升机制（原始诉求）

小6项目本身就是最好的"教材"。建议固化以下机制：

1. **代码审查轮值 + 双人复核**：所有改动至少一人 review；涉及工具沙箱/密钥的改动必须双人复核。
2. **周技术分享**：从本项目提炼主题——ACI 预判注入、Scene Protocol、SQLite WAL 与并发、记忆压缩、Python 标准库做后端。由团队成员轮流讲，逼大家吃透。
3. **规范文档固化**：`CONTRIBUTING.md`、`CODE_REVIEW_CHECKLIST.md`、本方案与《代码质量评审》作为团队基线。
4. **新人 onboarding**：用"拆 god-file"（Phase 1.1）作为第一个实战任务，既能练手又能直接产出价值。

## 五、风险与待决
