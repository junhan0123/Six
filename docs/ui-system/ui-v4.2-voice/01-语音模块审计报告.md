# 小6 UI · v4.2 Voice Presence Layer — 语音模块审计报告

> 审计对象：小6现有语音能力（wakeword / VOSK / Whisper / FunASR / ASR 模块 / SSE / EventBus）
> 审计目标：确认 v4.2「Voice Presence Layer」可在**不新增事件、不修改后端/运行时**的前提下，复用既有能力。
> 审计日期：2026-08-10

## 一、既有语音能力清单（后端，Python）

| 模块 | 路径 | 能力 | 前端是否可达 |
|---|---|---|---|
| ASR Provider | `xiao6-ui/asr.py` | 音频→文本；优先级 FunASR → Vosk → Whisper → 云端兜底 | **可达**（`/api/asr` 端点） |
| 中文唤醒词 | `xiao6-ui/kws.py` | 短音频转写 + 唤醒词判定 | 可达（`/api/kws`） |
| 英文唤醒词 | `xiao6-ui/wakeword.py` / `wakeword_vosk.py` | openwakeword「hey jarvis」常驻监听 | 服务端常驻，命中发 SSE |
| 事件总线 | `xiao6-ui/eventbus.py` | 唯一通信脊柱；`TOPIC_SSE` 扇出 | SSE 订阅可达 |

### 关键发现 1：后端 ASR **有 HTTP 端点**（此前 v4.1 审计遗漏，本次补全）

`server.py` 暴露：
- `POST /api/asr`（server.py:1280）—— 请求体为**原始音频字节**，扩展名由 `?ext=.webm` 指定（默认 `.webm`）；内部调用 `transcribe_bytes(data, ext)` → 返回 `{"ok":bool, "text":str, "error":str|null}`。**这是真实复用 VOSK/Whisper/FunASR 的入口。**
- `POST /api/transcribe`（server.py:1305）—— 音视频文件 → 字幕文本（复用同一 `transcribe_bytes`）。
- `POST /api/kws`（server.py:2353）—— 短音频（16k 单声道 WAV）→ `{"wake":bool, "transcript":str}`。
- `GET /api/asr/status`（server.py:426）—— 返回 `{"provider","enabled","local","available"}`，供前端探测。
- `GET /api/wakeword`（server.py:693）—— 常驻唤醒词状态/控制。

### 关键发现 2：语音状态**未**以前端五态形式推送

`eventbus.py` 的 `SYSTEM_EVENT_NAMES` 已注册 `wakeword_detected`（server.py 注释 server.py:2785 描述「前端语音循环每段断句后 POST /api/kws 判定」）。**但不存在 `voice_state` / `listening` / `speaking` 这类前端五态事件。** 即：后端不会把 LISTENING/PROCESSING/SPEAKING/ERROR 推给前端。

### 关键发现 3：既有 SSE 客户端与事件名已就绪（前端）

- `sse-manager.js`：`window.ZZSSE.onMessage(cb)` 提供统一 SSE 原始报文订阅（单 EventSource，自动重连）。
- `zz-events.js`：`SYSTEM_EVENTS.WAKEWORD_DETECTED = 'wakeword_detected'`，与后端 `SYSTEM_EVENT_NAMES` 逐字对齐（单一来源纪律）。
- `data-adapter.js`：`V4Data.onAgentState(cb)` 已订阅既有 `agent_state` SSE（agent_runtime 编排态）。

### 关键发现 4：Intent Gateway 入口已就绪（前端）

- `intent-gateway.js`：`ZZIntentGateway.dispatch(text)` → `POST /api/agent/intent`（与 v4 Intent Line 同一后端链路）。**语音识别文字进入现有 Intent Line 的唯一正确路径，不建第二个聊天框。**

## 二、红线符合性判定（审计结论）

| 红线要求 | 判定 | 依据 |
|---|---|---|
| 不新增事件 | ✅ 可行 | Voice Presence **仅订阅**既有 `wakeword_detected` 与 `agent_state` SSE；不调用 `publish/publish_system/publish_domain`。不触碰 EventBus。 |
| 不修改 Agent Runtime / EventBus / AppState / Goal / Memory | ✅ 可行 | 全部改动限于 `xiao6-ui/v4/` 表现层；不读不改上述模块。 |
| UI 只消费状态 | ✅ 可行 | 语音文字经既有 `/api/asr` 端点（消费）后，由 `ZZIntentGateway` 回投意图；状态仅订阅 SSE。 |
| 优先复用既有语音能力 | ✅ 完全满足 | 实时转写走既有 `POST /api/asr`（真实 FunASR/Vosk/Whisper）；唤醒走既有 `wakeword_detected` SSE；识别文字走既有 `ZZIntentGateway`。 |
| 不要重新实现语音 Runtime | ✅ 满足 | 不在前端重写 ASR；浏览器仅做**音频采集**（getUserMedia + MediaRecorder），识别交给后端既有 ASR。仅当后端 ASR 不可用时，降级为浏览器原生 `SpeechRecognition`（平台 STT，非自研），保证 Voice Orb 始终可用。 |
| 不新增聊天功能 / 不新增页面 | ✅ 满足 | 识别文字落入既有 Intent Line 输入框；无新页面、无 Dashboard、无第二个会话流。 |

## 三、设计边界（由此确定 v4.2 实现方案）

1. **采集**：浏览器 `getUserMedia` + `MediaRecorder` 取 webm/opus 音频字节（平台能力，非自研）。
2. **识别（主路径，忠实复用）**：每段录音 POST 到既有 `POST /api/asr?ext=.webm` → 后端 FunASR/Vosk/Whisper 转写 → 返回文本。
3. **识别（降级路径）**：若 `GET /api/asr/status` 不可用或 `/api/asr` 返回 err/空 → 用浏览器原生 `SpeechRecognition`（zh-CN）实时转写，保证 Voice Orb 始终可说话。
4. **唤醒触发**：订阅既有 `wakeword_detected` SSE，命中即进入 LISTENING（无接触唤醒）。
5. **文字落点**：`V4Intent.setText( interim )` 实时显示于 Intent Line；`V4Intent.submit( final )` 经既有 `ZZIntentGateway` 投出（与键入同一链路）。
6. **AI Core 联动**：Voice Orb 的五态以 `data-voice` 写在 `#aiCore` 上；复用既有 `agent_state` SSE 在语音指令投出后给一段 SPEAKING 生命反馈。不新增事件。

## 四、风险与已知限制（透明记录）

- **后端 ASR 依赖模型**：`/api/asr` 的准确率取决于 FunASR/Vosk/Whisper 模型是否就绪（server 启动时后台预热 whisper，见 asr.py:368）。若模型缺失且未配云端密钥，`/api/asr` 返回 `err` → 前端自动降级浏览器 STT，体验不中断。
- **HTTPS/localhost 约束**：`getUserMedia` 仅在 `https://` 或 `localhost` 可用。本地 `http://127.0.0.1:8121` 属安全上下文，可用。
- **`wakeword_detected` 触发频率**：取决于服务端 KWS/openwakeword 是否启用（`XIAO6_KWS_ENABLED`）。未启用时不影响点击/快捷键唤醒路径。
- **不修改后端**：本审计未、也不会改动任何后端文件；`/api/asr` 等端点按其既有契约消费。
