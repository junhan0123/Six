## 🔧 oMLX 崩溃监控 cron 深度排查

今日执行了约 10 次 oMLX 健康检查（每 ~20 分钟一次），发现多个严重 bug 并完成详细诊断。

### 当前运行状态（最终确认：正常）

| 项目 | 状态 | 详情 |
|------|------|------|
| oMLX 主进程 | ✅ 运行中 | PID 2043 (oMLX.app) |
| oMLX Server | ✅ 运行中 | PID 2063 (omlx-server) |
| 内存占用 | ✅ 正常 | RSS ~11GB（上限 48GB） |
| 监听端口 | ✅ 6259 | 实际监听端口 |
| API 响应 | ✅ 正常 | 返回 200 |
| 版本 | 0.5.7 | Build: 260804183110 |
| 配置 | ✅ 正确 | aggressive 模式，ceiling=48GB，ctx=64K |

### 发现的 Bug（按严重程度）

**Bug 1：监控脚本 PID 检测逻辑错误（严重）**
- 脚本用 `launchctl print` 获取 PID，但 LaunchAgent 的 `active count = 0`（launchd 认为服务未启动），返回空
- Fallback 搜索 `pgrep -f "omlx.cli serve"` 不匹配实际进程名 `omlx-server`
- 结果：脚本反复误判"进程不存在"并触发不必要的重启

**Bug 2：API 健康检查误报（严重）**
- 脚本用 `curl -sf -H "Authorization: Bearer ***"` 做健康检查
- `Bearer ***` 是伪造 Key，服务器返回 401，`-sf` 将非 2xx 视为失败
- 导致脚本反复误报"API 无响应"并触发不必要的重启

**Bug 3：端口冲突（中等）**
- oMLX 实际监听端口为 **6259**，但监控脚本检查的是 8000 端口
- 8000 端口被旧进程占用，新进程启动时 `Address already in use` 失败
- 导致日志中出现大量"启动后立即退出"记录

**Bug 4：LaunchAgent 状态不同步（低）**
- `ai.omlx.server` 状态为 `spawn scheduled`，但实际进程在运行
- launchd 日志（stderr 25MB + stdout 13MB）大量输出，建议定期轮转

### 修复建议

1. **修复 `monitor.sh` PID 检测**：改用 `pgrep -f "omlx-server"` 匹配实际进程名
2. **修复 API 健康检查**：接受 200 或 401 为正常（401 说明服务在运行）
3. **统一启动方式**：禁用 nohup 手动启动，统一使用 launchd 管理
4. **修复配置文件**：`settings.json` 中 `api_key` 字段为空，需补充
5. **清理大量日志**：launchd 日志已达 38MB
