## 🔥 近期重点（8月6日）

### 1. Hermes 配置深度优化（10:31）

**背景**：`jundot-oq6` 模型上下文窗口配置为 131072（128K），远超当前硬件稳定能力，导致 oMLX 运行时占用约 42GB 内存，频繁触发 OOM 风险。

**修改内容**：

| 配置项 | 修改前 | 修改后 | 原因 |
|--------|--------|--------|------|
| `model.context_length` | 131072 (128K) | **32768 (32K)** | 当前硬件稳定上限 |
| `model.max_tokens` | 未设置 | **8192** | 避免模型预留巨大输出空间 |
| `compression.abort_on_summary_failure` | false | **true** | 压缩失败时中止，不无限循环 |

**测试结果**：14 项测试全部通过（普通回答、文件读取、Terminal、连续 tool call、Memory、Skill、Obsidian、QQ、飞书、ComfyUI、oMLX API、Session reset、Agent loop guard、Compression）。

**备份文件**：
- `~/.hermes/backup_20260806_103330_final_optimization.yaml`
- `~/.hermes/config.yaml.bak_opt_20260806`

**完整报告**：`~/.hermes/Hermes_Final_Optimization_Report.md`

### 2. oMLX 崩溃根因审计（09:23 - 10:00）

**事件**：oMLX 进程 PID 70091 在 09:30:49 优雅退出，导致 Hermes 在 09:33 请求 `localhost:8000` 时 connection refused，触发 OpenRouter fallback。

**根因分析**：
- oMLX 收到外部信号后优雅 shutdown（非 crash、非 OOM）
- LaunchAgent `ai.omlx.server` 的 `KeepAlive.SuccessfulExit=false`，正常退出后不自动重启
- Watchdog `com.romlx.monitor`（每 120 秒执行）在 ~09:34 重启了 oMLX

**后续**：已建立 `~/.omlx/monitor.sh` 监控脚本，配置 aggressive 模式 + 48GB ceiling + 64K context 自动修复机制。

### 3. Cron Job 故障修复（17:46）

**发现的 3 个问题**：

1. **模型上下文窗口配置问题** — `jundot-oq6` 报告 32,768 tokens 上下文，低于 Hermes Agent 要求的 64,000 最小值，导致 `民权县每日天气` 和 `每日心灵鸡汤` job 失败。修复：清除 model metadata cache + 重启 gateway。

2. **每日对话重点归档 job 模型漂移** — job 创建时用的是 `qwen-oq6`，模型改为 `jundot-oq6` 后被安全机制拦截。修复：pin 到 `jundot-oq6`。

3. **手动触发验证** — 三个 job 全部成功执行。

### 4. Hermes 上下文异常诊断（02:13）

**现象**：Hermes session context 膨胀到约 99,612 tokens，接近压缩阈值 98,304，压缩机制失效，导致 iteration 7/500 持续 51 分钟重复循环。

**根本原因**：
- `context_length: 131072` 导致预填充空间过大
- 压缩 threshold 过低（50%），target_ratio 过于激进（20%）
- `abort_on_summary_failure: false` 导致压缩失败时无限重试

**已实施修复**：见上方第 1 点配置优化。
