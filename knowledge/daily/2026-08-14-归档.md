## ⚠️ 遗留问题（持续中）

### 1. monitor.sh 脚本 Bug（已多次报告，未修复）

监控脚本 `~/.omlx/monitor.sh` 第 119 行的健康检查使用了错误的认证头：

```bash
curl -sf --connect-timeout 10 http://127.0.0.1:8000/v1/models \
     -H "Authorization: Bearer ***"
```

`***` 是占位符，真实 Key 是 `sk-omlx`（存储在 settings.json 的 `auth.api_key` 字段）。

**影响**：每次健康检查返回 401，`-sf` 标志把 401 当成错误（exit code 22），脚本会误判为"API 无响应"并触发不必要的重启。

**历史证据**：日志中多次出现 `⚠️ oMLX 进程存在但 API 无响应，重启`，实际服务正常。

**建议修复**：
- 方案 1：去掉认证头（本地脚本不需要鉴权）
- 方案 2：从 settings.json 动态读取真实 Key

### 2. LaunchAgent 状态异常

`ai.omlx.server` 显示"spawn scheduled"，实际进程通过 nohup 启动，非 launchd 管理。系统重启后可能无法自动拉起。
